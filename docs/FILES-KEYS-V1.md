# Files custody and service contracts v1

Added 2026-10-03. These contracts are additive. Existing Ed25519 Member Keys, authentication presentation bytes, namespace-registration signatures, Castaway records, signing recovery, snapshots and catalog schemas remain unchanged.

`FilesKeyBindingV1` has the fixed JSON field order `schema`, `ownerMemberKey`, `serviceId`, `storageAccountId`, `namespaceId`, `workspaceId`, `submissionId`, `revisionId`. All identifiers except the bounded opaque account ID are lowercase 32-byte hex. The service identity is the pinned index receipt key; it is not a universe or federation identity. A fresh random revision identifier is allocated before encryption. Ciphertext hashes are verified separately, avoiding a circular AAD dependency.

The root remains inside custody. Rust derives a 32-byte wrapping key with BLAKE3 `derive_key("castalia/files-key-wrap/v1", recoveredEd25519Seed32)`. AES-256-GCM wraps only the selected 32-byte revision data key with the fixed-order binding JSON as additional authenticated data. The envelope contains exactly schema, binding, canonical base64url 12-byte nonce and 48-byte ciphertext. Each data revision uses a fresh key and nonce. The shared browser worker encrypts its bounded transport with that same binding as AAD. No passphrase, root or wrapping key is returned to the application; selected revision keys are transient and worker inputs are wiped.

The requesting origin appears in fresh explicit consent, not key derivation. Independently approved Castalia and Zenith requests can therefore unwrap the same existing-wallet envelope. Files consent binds the typed operation, exact request digest, audience, actual origin, nonce and a maximum 120-second ceremony. Replay, cancellation, lock, disposal, origin changes and owner changes fail closed. An expired consent ceremony does not invalidate previously signed evidence or an existing envelope; a new ceremony is required to open it.

The narrowly typed service-authentication method signs only the existing eight-field Auth transcript with `castalia-files://index/<key>` or `castalia-files://gateway/<key>` audiences. No unrestricted signer is exposed. The server verifies the same owner key, exact origin, one-use challenge and deadline before creating a bounded session. Sessions are kept in memory by the browser. Ordinary authentication does not replace the separately verified registration signature or base-membership eligibility.

Service envelopes use sorted `canonicalJson(payload)` and Ed25519 signatures. Parsers reject unknown fields and schema versions. Upload intents bind operation ID, owner/destination, expected previous head, ciphertext hash/size and gateway. A storage receipt additionally binds exact immutable object key/version and the pinned s3d revision with zero pending and unpinned object counts. Index acceptance binds the intent, registration genesis, descriptor digest, storage receipt digest, revision sequence and previous head. Neither S3 metadata nor a flush acknowledgement is an application head.

Implementations and synthetic fixtures in Wallet and Web use the same typed consent helper. Their historical source permissions remain separate from integrity checks and this new contract. See SOURCE-PROVENANCE.md and the preserved licensing findings.
